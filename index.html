Flowchart Notation Reference

What Is a Pseudocode Diagram?

A pseudocode diagram (flowchart) is a visual representation of a process — the logic made visible. It maps every decision, action, and data flow using standardized shapes connected by directed arrows. Unlike written code, it is language-agnostic and readable by anyone.

A recipe is the perfect starting structure: it has ingredients (inputs), steps (processes), conditional judgments ("if not done, continue"), and a finished dish (output).

Core Concepts to Master

  • Every process has exactly one START and one END
  • Shapes carry specific semantic meaning — don't improvise
  • Arrows show direction and control flow, never reversed arbitrarily
  • Decisions always branch into exactly two paths: YES and NO
  • All paths must eventually reconnect or reach END
  • Loops require a re-entry arrow pointing backward
  • Keep each box to one atomic action or decision
01
Vocabulary

Shape Reference — What Each Box Means

Each shape in a flowchart is a symbol with a specific, non-negotiable meaning. Using the correct shape is as important as using the correct notation in architectural drawing.

START / END
Oval / Terminator
"Begin: Gather your mise en place"

Marks the single entry point (START) and all exit points (END) of the algorithm. Rounded edges signal the boundary of the process.

PROCESS
Rectangle / Process
"Dice the onion into 5mm cubes"

Any action, calculation, or transformation. The workhorse of the diagram. Should describe one atomic operation — one verb, one object.

YES/NO ?
Diamond / Decision
"Is the sauce reduced by half?"

A binary question with exactly two exits: YES (TRUE) and NO (FALSE). Never use for multi-way branches without chaining multiple diamonds.

INPUT / OUTPUT
Parallelogram / I/O
"Add 2 cups of flour" / "Serve the dish"

Data entering (ingredients/measurements) or leaving (final output) the system. The skew distinguishes it from process boxes at a glance.

SUB-PROCESS
Rounded Rectangle
"Make the roux" (a whole sub-recipe)

A predefined sub-process or function — a named block of steps defined elsewhere. Use this when a step is itself a complete algorithm.

CALLED PROCESS
Rectangle with Ears
"Refer to base stock recipe"

Indicates a call to an external procedure. The vertical bars on the sides signal that control leaves and returns. Common in modular recipe systems.

02
Connectors

Arrow Types — How to Connect Boxes

Arrows are not decoration — they encode direction, condition, and flow priority. Every arrow must be directed (have an arrowhead). No bidirectional arrows in standard flowcharts.

Standard Flow Arrow

Default connector between any two sequential steps. Solid line, single arrowhead. Flows top → bottom or left → right.

"Heat pan → Add oil → Add onions"

Y
N
Decision Branch — YES / NO

Always label both exits from a diamond. YES (green/right) and NO (red/left) paths. Label must sit near the arrowhead, not the diamond.

"Is pasta al dente? Y → drain / N → continue boiling"

Dashed / Conditional Arrow

Optional path or dependency. Use when a step may occur depending on context but isn't part of the main flow. Rare in basic diagrams.

"Optionally: add truffle oil before serving"

Loop-Back Arrow

Returns flow to a previous step. Always drawn as a curved or angled path on the outside of the main flow column — never crossing other arrows.

"Taste → Adjust seasoning → Taste again"

Arrow Routing Rules All primary flow goes vertically top-to-bottom or left-to-right. Loop-back arrows travel along the outside edge of your diagram. When arrows must cross, draw a small bridge arc over one line. Label every decision arrow. Label every loop-back with the condition that keeps it looping (e.g. "not done").
03
Method

Step-by-Step: Recipe → Pseudocode Diagram

We will convert a simple pasta recipe into a complete flowchart. Follow each step before moving to the next — the diagram only works when built in order.

1

Read the Entire Recipe First — Identify All Actions

Before drawing a single box, read the recipe completely and annotate every verb. Each verb is a potential process node. Underline conditional phrases ("if", "until", "while", "check") — those become decision diamonds.

// EXAMPLE RECIPE — Spaghetti Aglio e Olio 1. Boil salted water 2. Cook spaghetti until al dente ← DECISION 3. Meanwhile, slice garlic thin 4. Toast garlic in olive oil until golden ← DECISION 5. Add chili flakes 6. Reserve pasta water 7. Drain pasta 8. Toss pasta with oil + water 9. Taste → adjust salt ← DECISION 10. Plate and serve

Annotation result: 7 process nodes, 3 decision diamonds, 2 parallel tracks (pasta + garlic happening simultaneously).

2

Write the Pseudocode in Plain Language

Convert your annotated recipe into structured pseudocode — a formalized plain-English logic script. Use indentation to show nesting. This is your blueprint before you draw.

BEGIN SpaghetttiAglioeOlio INPUT: spaghetti, garlic, olive_oil, chili, salt, pasta_water boilWater(salt) cookPasta(spaghetti) WHILE pasta.texture != "al dente" DO continueCooking(pasta) END WHILE // Parallel sub-process (garlic track) sliceGarlic() toastInOil(garlic, olive_oil) WHILE garlic.color != "golden" DO continueToasting(garlic) END WHILE addChiliFLakes() reservePastaWater() drainPasta() toss(pasta, oil_mixture, pasta_water) taste() IF seasoning != "balanced" THEN adjustSalt() END IF OUTPUT: plate(dish) END
3

Sketch the Skeleton — Start with START and END

On paper or in your diagramming tool, place your START oval at the top center. Place your END oval at the bottom. Draw a single vertical center line between them — this is your spine. Everything connects to this axis.

Spatial Rule Leave generous vertical spacing between nodes — at minimum 1.5× the height of your largest box. Cramped diagrams are unreadable. In professional practice, diagram width rarely exceeds a single screen column.
4

Place Process Boxes — One Action Per Box

Working down from START, add a rectangle for each sequential action. Write the text in the imperative mood: "Boil water", "Slice garlic". Each box should be the same width. Never write more than one action in a single rectangle — split it if necessary.

Text Rule Box labels should be concise (3–7 words), action-first. Never use passive voice inside a process box. Bad: "The water is boiled." Good: "Boil salted water."
5

Insert Decision Diamonds at Each Conditional

Every "WHILE", "IF", or "UNTIL" in your pseudocode becomes a diamond. The question inside must be answerable with YES or NO only. Place the YES exit going down (continuing the main flow) and the NO exit going left or right (to a loop-back or alternate path).

DIAMOND: "Al dente?" YES → continue to next step (drain pasta) NO → loop back to "Continue cooking" rectangle

The loop-back arrow travels outside the right edge of your column, curves back up, and re-enters the top of the "Continue cooking" box.

6

Draw Parallel Tracks for Simultaneous Processes

In cooking, two processes often run in parallel (boiling pasta while making the sauce). In a diagram, parallel tracks are shown by splitting the flow into two columns using a horizontal bar (or just two separate vertical columns) and rejoining before the next shared step.

// SPLIT at: "While pasta cooks..." [horizontal fork bar] LEFT COLUMN: cookPasta → [Decision: al dente?] → drain RIGHT COLUMN: sliceGarlic → toastInOil → [Decision: golden?] → addChili [horizontal join bar] // MERGE at: "Combine both"
7

Add Input / Output Parallelograms

Place a parallelogram just after START to declare all ingredients (inputs). Place another at the END sequence to mark the "Serve dish" output. If the recipe has mid-process data (e.g., "measure reserved pasta water"), add an I/O parallelogram at that point too.

8

Label All Arrows — Review Every Connection

Walk every arrow in your diagram and verify: (a) it has an arrowhead, (b) it points in the correct direction, (c) every diamond exit is labeled YES/NO. Trace every possible path from START to END to confirm it terminates. Any path that doesn't reach END is a logical error — fix it before finalizing.

Final Checklist ① Exactly one START and one END · ② Every shape uses the correct type · ③ Every arrow is directed · ④ Every diamond has exactly two labeled exits · ⑤ All loops have a termination condition · ⑥ No paths lead to dead ends · ⑦ Parallel tracks fully merge before END

05
Quality Control

Visual Design Rules — Do's and Don'ts

A flowchart is a communication tool. These principles separate a legible professional diagram from a confusing one.

Element DO AVOID
Box Size Keep all process boxes the same width. Height adjusts to text. Varying box widths arbitrarily — it implies significance that isn't there.
Alignment Center-align all boxes on a single vertical axis for the main flow. Scattering boxes across the canvas with no structural grid.
Arrow Length Keep arrows short and direct. Long arrows signal poor layout — rearrange the diagram instead. Crossing arrows. If unavoidable, use a bridge arc to indicate non-connection.
Text Use one consistent sans-serif or monospace typeface. Sentence case. 3–7 words per box. Full sentences, passive voice, or abbreviations that aren't established conventions.
Color Assign color by shape type (semantic). Use a maximum of 4–5 colors. Always include a legend. Random or decorative color use. Never color the same shape type differently within one diagram.
Loop Routing Route loop-back arrows along the outer edge of the column, always on the same side. Loop-back arrows going through the center of the diagram or crossing primary flow arrows.
Density Leave 1–2× box-height of white space between each node. Let the diagram breathe. Compressing the diagram to fit a page — use multiple pages or a legend for large processes.
Decision Labels Always label both exits of every diamond. Place label near the arrowhead. Unlabeled decision exits or labels placed at the diamond body instead of the arrow.
